# Photo lifecycle

Spoonjoy stores uploaded and generated photos in the `PHOTOS` R2 bucket (`spoonjoy-photos` in production, `spoonjoy-photos-qa` on QA) and serves them publicly from `/photos/<key>`. Before the photo sweep, deleting a spoon, archiving a cover or deleting a recipe only changed a database row: the object stayed in R2 and stayed public forever.

The photo sweep (`app/lib/photo-lifecycle.server.ts`) finds objects that nothing references any more and removes them in two reversible steps. It runs from the Worker's cron trigger (`triggers.crons` in `wrangler.json`, every six hours) in the mode set by `PHOTO_SWEEP_MODE`.

## What counts as referenced

A key is live while any of these rows refers to `/photos/<key>`:

- a user's profile photo (`User.photoUrl`);
- a spoon that is not deleted, on a recipe that is not deleted (`RecipeSpoon.photoUrl`);
- a cover that is not archived, on a recipe that is not deleted (`RecipeCover.imageUrl`, `stylizedImageUrl` and `sourceImageUrl`).

Forks copy their source's cover row and keep the same R2 key, so a key stays live as long as any fork still uses it, even after the original recipe is deleted. Size variants (`variants/w<width>/<key>.webp`) follow their original.

## Modes

| `PHOTO_SWEEP_MODE` | What a run does |
| --- | --- |
| `dry-run` (default, and anything unrecognised) | Lists the bucket, records each newly unreferenced key in `PhotoCleanup`, writes a `PhotoSweepRun` report and logs it as `spoonjoy.photo_sweep`. R2 is not touched. |
| `apply` | Also moves each eligible key to `quarantine/<key>` (never served by `/photos/`), deletes its variants, deletes orphaned variants, and purges quarantined objects whose retention has passed. |
| `off` | Nothing. |

A key becomes eligible 7 days after the sweep first sees it unreferenced (`PHOTO_SWEEP_GRACE_MS`). Photos of a deleted account are queued by the deletion itself and are eligible straight away, but the sweep still checks that nothing references them, so a photo shared with another cook's fork is kept. A quarantined object is purged 30 days after it was moved (`PHOTO_QUARANTINE_RETENTION_MS`). Each run makes at most 200 moves and purges; the rest wait for the next run (`truncated` in the report).

Safety checks in `apply` mode:

- If the reference query finds no live photos at all while the bucket holds photos, the run refuses to move anything (the query is wrong, not every photo unused).
- Each key is checked for references again immediately before it is moved.

## Reading the reports

```sh
pnpm exec wrangler d1 execute spoonjoy --remote --command \
  'SELECT "startedAt", "mode", "objectsScanned", "referencedObjects", "unreferencedObjects", "unreferencedBytes", "orphanVariants", "eligibleObjects", "quarantined", "purged", "failures", "truncated", "note" FROM "PhotoSweepRun" ORDER BY "startedAt" DESC LIMIT 5'
```

Use `spoonjoy-qa` for QA.

## Switching removal on

Removal is a production data change, so it stays a dry run until a person has read the dry-run counts and decided. To switch it on, change `PHOTO_SWEEP_MODE` to `apply` for the environment in `wrangler.json` in a reviewed pull request. To stop it again, set it back to `dry-run` (or `off`) and deploy.

## Undoing a move

Until it is purged, a quarantined photo can be put back:

1. Copy `quarantine/<key>` back to `<key>` with the same content type (the original key and the move time are in the object's custom metadata `originalKey` and `quarantinedAt`):

   ```sh
   pnpm exec wrangler r2 object get "spoonjoy-photos/quarantine/<key>" --remote --file restore.bin
   pnpm exec wrangler r2 object put "spoonjoy-photos/<key>" --remote --file restore.bin --content-type image/jpeg
   pnpm exec wrangler r2 object delete "spoonjoy-photos/quarantine/<key>" --remote
   ```

2. Delete the key's `PhotoCleanup` row, so the sweep treats it as new:

   ```sh
   pnpm exec wrangler d1 execute spoonjoy --remote --command 'DELETE FROM "PhotoCleanup" WHERE "key" = '"'"'<key>'"'"''
   ```

3. Make sure a live row references `/photos/<key>` again (for example un-archive the cover), or the sweep will find it unreferenced and start the grace period again. Size variants are regenerated by the Photo variants workflow.
